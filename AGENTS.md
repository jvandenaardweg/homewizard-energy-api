# AGENTS.md

This is a typed Node client for the HomeWizard Energy local API: API v2 over HTTPS (P1 meter, kWh meters, Plug-In Battery) at the package root, and the frozen API v1 over HTTP (P1 meter, Energy Socket, water meter, kWh meters) under `homewizard-energy-api/v1`, with mDNS device discovery. The upstream docs are at https://api-documentation.homewizard.com, with their source in the `homewizard/api-documentation` GitHub repo. It is published to npm as `homewizard-energy-api`, and usage docs live in `README.md`, with the frozen API v1 in `docs/v1.md` and the upgrade guide in `docs/upgrading.md`.

## Verifying changes

- `npm test` is the full gate: lint (including Prettier formatting), type-check, then vitest with coverage. Aim for 100% coverage, so new code comes with tests for each branch. It's a target, and the config doesn't enforce a threshold. The husky pre-commit hook runs lint-staged to format staged files, then `npm test`, whose `prettier --check .` also reads unstaged files, so format those first or the commit fails.
- To run a single test file: `TZ=Europe/Amsterdam npx vitest run src/telegram/telegram.test.ts`. Always set `TZ=Europe/Amsterdam`, because telegram timestamps are formatted in local time and the expected test values are hard-coded to Amsterdam offsets.
- `npm run test:package` checks what `npm test` can't, because the tests run from `src`: it builds and packs the package, installs the tarball into an empty project, loads each entry point with `import` and `require()`, type-checks them with `nodenext` and `bundler` resolution, and type-checks the TypeScript examples in `README.md` and `docs/v1.md` (`scripts/check-package.mjs`). Run it after changing `package.json` exports, the build, an export or a README example. CI runs it.
- The scripts in `src/examples/` are the full versions of the README recipes, and each recipe ends with a link to its script. They import the package by its name, as users do (the `paths` in `tsconfig.json` for tsc and tsx, and the aliases in `vitest.config.mts`), read the credentials from the `devices.json` that `src/examples/pair.ts` writes (git-ignored), and run with `npx tsx` against a real device. `src/examples/examples.test.ts` runs each one against the mocks, through a mock of the package that adds the mock dispatcher (or the test CA for the WebSocket) and a memory store, and checks that each README recipe links a script that exists; `src/examples/v1/examples.test.ts` does the same for the API v1 and the recipes in `docs/v1.md`. A new recipe needs a script and a test there.

## Compatibility

- The supported runtime is Node >=22.19 (`engines.node`), the lowest version undici 8 supports. CI tests Node 22, 24 and 26, and the TypeScript target and lib are ES2024. Use only APIs that Node 22.19 offers. The runtime dependencies are `undici` (HTTP, the TLS agent and the WebSocket) and `multicast-dns`, plus `@types/multicast-dns`, because the shipped declarations use its types.
- The package is ESM (`"type": "module"`), and CommonJS users load it with `require(esm)`. Imports in `src` stay without an extension; `tsc-alias` adds `.js` in `dist` (`resolveFullPaths` in `tsconfig.json`), so Node can load them.
- The dev tooling needs a newer Node than the library: release-it supports `^22.22.2 || ^24.15.0 || >=26`, and vitest doesn't list Node 25. Develop on the version in `.nvmrc`.
- The toolchain doesn't load the TypeScript compiler API, so `typescript` can be TypeScript 7, which has none: Oxlint lints, tsx runs `src/examples/`, and tsc-alias rewrites the `@/` paths. Keep it that way, or a tool will need TypeScript 6 again.
- The public API is the three entry points in the `exports` map of `package.json`: `.` (`src/index.ts`), `./v1` (`src/v1/index.ts`) and `./telegram` (`src/telegram/index.ts`). A new entry point needs both an `exports` and a `typesVersions` entry. This is a semver library, so renaming or removing an export or a response field is a breaking change.

## Architecture

- The package root is the API v2, which talks HTTPS with a token. `src/v1/` is the API v1 (HTTP to `/api/v1`), frozen until HomeWizard removes it: it gets fixes, and no new endpoints or devices. Both build on `src/shared/` (request with timeout, logger, polling loop, mDNS discovery, `AsyncQueue`, `StreamSet`), which keeps the v1 classes' public and protected API unchanged. `src/shared/` imports nothing from `src/v1/` or the root, so `src/v1/` can be deleted in one piece when HomeWizard removes the API v1, together with its mocks in `src/mocks/v1/` and its examples in `src/examples/v1/`. The telegram parser in `src/telegram/` serves both.
- `src/endpoints.ts` has one function per endpoint, taking the internal `Client` (`src/client.ts`: TLS agent, token, `X-Api-Version`). The device classes in `src/devices/` extend `Device`, which holds what every device supports, and add only the endpoints their device supports, following the capability matrix in `docs/architecture.md`. A device without an endpoint has no method for it.
- The device classes take `(credentials, options?)`: `Credentials` (`{ host, token, identifier }`) is what `pair()` returns and users store as one value, and `ConnectionOptions` holds how to connect (timeout, logger, insecure, dispatcher, ca). `src/credentials-store.ts` stores credentials per key (`createFileStore()`, `createMemoryStore()`, or the user's own `CredentialsStore`); nothing else in the library reads a store.
- The device classes, `pair()`, `connect()`, `discover()` and the credentials stores throw, and the WebSocket emits, one `HomeWizardError` (`src/errors.ts`) with a `kind` and the device's `code`. `src/transport-errors.ts` turns a failed request or WebSocket connection into its kind, with the original as `cause`: `Client` passes its `requestErrors` (one factory each for a timeout, an error status and invalid JSON) to `requestWithTimeout()` and `readResponse()` in `src/shared/request.ts`, as `BaseApi` passes the v1 ones from `src/v1/errors.ts` to `requestWithTimeout()` and `parseJsonResponse()`, and both `Client.send()` and the WebSocket `Connection` wrap what they catch through its `toHomeWizardError()`. undici's WebSocket reports a failed connection without its TLS or network error, so on the WebSocket that is always kind `socket`. A `GET` that fails with a `timeout` or `network` error is retried, per the `retries` option. `discover()` wraps the mDNS errors of the shared `MdnsDiscovery` too. Pairing retries the `timeout` and `network` kinds, and throws any other kind straight away: everything in its loop throws a `HomeWizardError`, including the check of the user name.
- The API v2 checks the device's certificate: the HomeWizard CA, and the Common Name against the `identifier` (`appliance/<type>/<serial>`). The device classes require the identifier unless `insecure: true`; only `pair()` connects without one, to learn it from the certificate. `IdentifierPolicy` (`src/identifier-policy.ts`) holds these rules (pinned, learn or insecure), and `Client` takes it instead of the identifier and `insecure`. Values from mDNS are untrusted, so `connect()` compares the discovered `id` with the stored identifier. Tokens stay out of logs: log bodies through `redact()`.
- Pushed data has events and async iterators side by side: the WebSocket has `socket.on()` and `socket.stream()`, and discovery is `discover()` only. The streams of a poller and of a socket topic open through a `StreamSet` (`src/shared/stream-set.ts`), which feeds each stream's `AsyncQueue` from the events, removes its listeners when it ends, and decides which stream stops the source. `discover()` feeds an `AsyncQueue` of its own. The device classes have no `polling` getter: the WebSocket pushes changes, and `poll(fn)` (`src/poll.ts`) polls any method, with events or `stream()`.
- In v1, `BaseApi` (`src/v1/base-api.ts`) holds the request, error, logging and polling logic as `protected` methods, and each device class re-exposes the methods its device supports as public overrides. Polling is `api.polling.<method>.start() / stop() / on('response' | 'error', …)`, backed by one EventEmitter per instance that emits method-scoped events (`getData:response`). Subclasses override these protected methods, and the protected finders of `MdnsDiscovery`, so the built-in code calls each one as it did in the release: `src/v1/subclass-contract.test.ts` pins every call.
- Response types in `src/types.ts` and `src/v1/types.ts` mirror the upstream API exactly. Field names stay snake_case, and data points are optional because devices omit null values. Each field's JSDoc names the devices that send it ("Available for: `HWE-P1`"), and each type has an `@link` to the upstream docs. Those links point at https://api-documentation.homewizard.com (the old `homewizard-energy-api.readthedocs.io` site is offline). These comments ship in `dist` as editor docs.
- Both `@/` alias imports and relative imports appear in `src`. The `@/` alias works in `dist` only because the build rewrites it with `tsc-alias`, and vitest resolves it through its own alias in `vitest.config.mts`.

## Adding an endpoint or device

The change is done when every applicable item is covered:

1. The function goes in `src/endpoints.ts`, and the method on each device class in `src/devices/` whose device supports it, per the upstream docs.
2. Types go in `src/types.ts`, and a new WebSocket topic in `src/websocket/types.ts`.
3. Fixtures go in `src/mocks/data/v2.ts`, mocked with `mockV2()` from `src/mocks/api-v2.ts`.
4. Tests go in `src/endpoints.test.ts` and the table in `src/devices/devices.test.ts`, including the device's `missing` methods.
5. For a new device, add an example to `src/examples/` with its test in `src/examples/examples.test.ts`, and its product type to `ProductTypeList` in `src/types.ts`, `CERTIFICATE_PRODUCT_TYPES` in `src/tls.ts` and `DEVICE_CLASSES` in `src/discovery.ts`, export it from `src/devices/index.ts`, and add it to the README's method table. When the device also has a v1 class, that class stays in `src/v1/` until upstream removes the API v1.

## Tests

- `vitest.setup.ts` installs the global undici `MockAgent` from `src/mocks/agent.ts`, with real network disabled, and it turns on fake timers before every test.
- Each request needs its own interceptor (`mockV2()` from `src/mocks/api-v2.ts`, or `apiMocks.<name>()` from `src/mocks/v1/api.ts` in v1), because an interceptor is used up after one reply.
- The API v1 mocks and fixtures live in `src/mocks/v1/`, and go with `src/v1/` and `src/examples/v1/`, which are deleted together. Tests outside those folders import from neither and use a v2 or neutral fixture, so they keep passing once all three are deleted.
- Discovery tests replace `multicast-dns` with `vi.mock`, using helpers from `src/mocks/mdns-v2.ts`, and from `src/mocks/v1/mdns.ts` in v1.
- The device classes create their own TLS agent, which bypasses the global `MockAgent`, so tests pass it as `dispatcher`: `new P1Meter(mockV2Credentials, { dispatcher: mockApiAgent })`. The internal `Client` takes `mockV2DeviceOptions`.
- The WebSocket logic is tested on fakes with fake timers: `DeviceSocket` on `FakeConnection` (`src/mocks/websocket-connection.ts`, set as `connectionClass` in a subclass), and `Connection` on a fake undici `WebSocket` in `connection.test.ts`.
- The certificate checks, and the WebSocket tests of the certificate, a wrong token and one happy path, need a real TLS handshake, which `MockAgent` skips. Those tests use the local server in `src/mocks/tls/` (a test CA with two device certificates, `useOtherDevice()` to switch between them, and a minimal WebSocket server that scripts a device) with real timers: call `vi.useRealTimers()` in `beforeEach` and `vi.useFakeTimers()` again in `afterEach`, because the global `afterEach` runs the fake timers.

## Commits and releases

- Commit messages follow Conventional Commits (`feat:`, `fix:`, `chore:`), because the changelog and the version bump are built from them. `@release-it/conventional-changelog` groups the release notes by type, in this order: breaking changes, `feat`, `fix`, `perf`, `revert`, `docs`, then `refactor`, `test`, `chore`, `ci`, `build` and `style` under "Other Changes". A commit without a recognised type is left out. Each release ends with a Contributors section that credits commit authors and `Co-authored-by` trailers, leaving out the maintainer, bots and AI agents (the filters and the GitHub profile lookup are in `.release-it.cjs`). Use `docs:` for JSDoc changes in `src/types.ts`, since they ship to users as editor docs.
- A `BREAKING CHANGE:` footer describes the change against the last release, so leave it off changes to API that hasn't shipped yet.
- `CHANGELOG.md` is written by that plugin during `npm run release`, so edits belong in commit messages, not in that file.
- Release only when the maintainer asks for it. The steps, checks and failure fixes are in the `release` skill (`.claude/skills/release/SKILL.md`).
